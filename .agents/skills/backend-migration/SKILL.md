# Backend Migration

Make the requested schema change while keeping SQLAlchemy metadata and Alembic
history consistent.

## Inspect

Before editing:

1. Read the root and API `AGENTS.md` files.
2. Inspect the affected SQLAlchemy mappings.
3. Inspect the current Alembic heads and neighboring migrations.
4. Determine whether the request changes schema, data, or both.
5. Preserve existing naming and type conventions.

Do not rewrite migration history that may already be applied. Create a new
revision unless the user explicitly requests modification of an unreleased
migration.

## Implement

Update the SQLAlchemy mappings before generating an autogenerated migration.

Generate the revision from the repository root:

```bash
uv run --env-file .env --project apps/api \
  alembic -c apps/api/alembic.ini revision --autogenerate -m "<message>"
````

Review the generated migration. Do not accept autogenerate output blindly.

Check:

* table and column names
* PostgreSQL types
* nullability
* indexes and unique constraints
* foreign-key actions
* server defaults
* constraint names
* upgrade operation order
* downgrade operation order

Use explicit data-migration steps when existing rows make a schema operation
unsafe. Do not assume a table is empty unless the repository or task establishes
that fact.

## Verify

Apply all migrations:

```bash
uv run --env-file .env --project apps/api \
  alembic -c apps/api/alembic.ini \
  revision \
  --autogenerate \
  --rev-id <next-three-digit-revision> \
  -m "<message>"
```

Verify the current revision:

```bash
uv run --env-file .env --project apps/api \
  alembic -c apps/api/alembic.ini current
```

When safe for the local test database, verify rollback and re-apply:

```bash
uv run --env-file .env --project apps/api \
  alembic -c apps/api/alembic.ini downgrade -1

uv run --env-file .env --project apps/api \
  alembic -c apps/api/alembic.ini upgrade head
```

Then run the relevant backend checks and integration tests.

## Report

Report:

* mapping changes
* revision identifier
* upgrade behavior
* downgrade behavior
* verification results
* any data-safety assumption
